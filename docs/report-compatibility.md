# Saved Report Compatibility

[PRODUCT](PRODUCT.md#reporting-and-coverage) owns the current report contract. `locmetry --schema report` describes structural validity; comparison eligibility additionally requires recorded detail. [Contract types](../src/contract.rs) own serialization, deserialization and schema descriptions, using the same schema generator as configuration. [Validation](../src/contract/validation.rs) checks arithmetic and recorded identities internally; no public `validate` command is provided.

Early pre-release S1–S5 checkpoints still identified as 0.1.6; their counters differ from the v0.1.6 release despite that string. `0.2.0-dev.1` corrected the producer identity before the `0.2.0` release. Existing exports from those early checkpoints cannot be reliably distinguished by version alone; regenerate them with an identified build when that distinction matters.

All these reports use `schema_version: "1"`. Optional file records require `--files`; headline/full projections have different evidence even within one release. `source` and empty summary maps can be omitted for zero totals. Nullable configuration paths mean no loaded file; omitted historical provenance means the producer did not record it. The typed reader preserves absent personal-config provenance, unclassified-folder evidence and the pre-v0.1.2 module switch as absent, as it does missing failure evidence. New measurements resolve defaults and emit their effective values. Every tagged fixture is checked for value-preserving round trips; JSON object key order is not part of compatibility.

## Validation boundaries

Counts are nonnegative `u64` values. Semantic validation uses checked addition, verifies `lines = code + comments + blanks`, reconciles summary dimensions, coverage, workspace members and available breakdown/file detail, and rejects duplicate identities in array rows. Language summary file counts measure participation and may overlap; they cannot exceed source physical files or fall below the host-file counts established by breakdown rows, globally or per member; embedded breakdown rows have zero files and remain additive. Missing aggregate keys mean zero only where the contract permits it. Explicit zero summary entries are equivalent to omission.

Unknown object fields and invalid enums are rejected at typed boundaries, including effective policy. Configuration snapshots share the configuration parser's types; the JSON report schema retains JSON null semantics, while TOML schemas remove null as a format-specific constraint. Backend mapping display names and enum aliases are both accepted, matching Tokei's parser. This tightens validation of malformed reports without changing valid current measurement output.

Duplicate raw JSON keys in dynamic maps retain the last value under the existing deserializer. Schema and semantic validation see that resulting map; they do not promise to detect overwritten keys. This is distinct from duplicate array-row identities, which are rejected.

## Comparison evidence

A structurally valid headline is not a full comparison input. The internal eligibility check requires `review`, `breakdown`, `metadata.kinds`, `metadata.modules`, `metadata.coverage.unrecognized`, and effective `config` for the root or every workspace member. Missing sections are named in the error; an absent module list cannot be replaced with invented empty evidence. File records are optional.

The [net-change command](PRODUCT.md#net-change) reports missing historical failure evidence as a coverage finding, without treating that absence alone as an observed failure. Old notebook exports can contain doubled or missing counts even when marked accurate; structural validity cannot retrospectively establish measurement correctness. Forward compatibility is not guaranteed: older strict schemas may reject newer optional fields and should be updated from the producing executable.

## Subfolder Selection

Version-1 reports may include `metadata.scope.subfolder`, a normalized project-relative measured directory. Consumers must inspect this field before treating `summary` as whole-project totals. Absence means no subfolder restriction; historical reports retain absence when decoded and reserialized. Context modules may lie outside the restriction, but measured file/coverage/review paths must lie inside it; folder summaries can retain applicable project-relative ancestors. The reader rejects malformed restrictions and workspace-member restrictions. Comparison refuses differing restrictions, including present versus absent. Older strict readers may reject this additive field; silently removing it would misrepresent measurement scope. [PRODUCT](PRODUCT.md#subfolder-measurement) owns the supported semantics.
