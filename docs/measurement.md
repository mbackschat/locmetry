# Measurement Semantics and Limits

[PRODUCT.md](PRODUCT.md) owns the configuration, measurement model, and report schema, and the [README](../README.md) shows CLI usage. This page records selection and counting details, known limits, and this repository's private regression.

## Selection and Paths

- Untracked nonignored files are included. With ignore files respected, `.ignore` and `.tokeignore` files always apply and `.gitignore` applies only inside a Git work tree. Symbolic links are not followed.
- Selection reads ignore files, not the Git index: a tracked file under an ignored path, such as one added with `git add -f`, is not measured, and `explain` reports it as not selected by ignore policy. `--respect-ignore-files false` measures it, along with every other ignored file.
- Exclusions are checked again against the backend response, so excluded files cannot leak into counts.
- Counting parses selected files directly without another directory walk; replacing a selected file with a directory cannot introduce its children into the counts. Selection and reads are not a filesystem snapshot.
- Rules match root-relative `/`-separated paths. Components come from the platform's path parser, so Unix file names may contain `:` or `\`.
- An output path inside the scan root or equal to the configuration is rejected before scanning, so a report never measures itself or replaces its policy; in workspace mode the same holds for every member and the workspace file.

`locmetry explain PATH` uses this same selection and the same per-file counters/classifier, while counting only the target. It traverses selected names to preserve module inference. Ignore/hidden probes establish only whether a single setting changes selection; they do not identify an ignore-file line or recover a historical report's scope. See the [troubleshooting guide](guides/selection.md) for path bases, states and limitations.

## Subfolder Context and Coverage

[The subfolder contract](PRODUCT.md#subfolder-measurement) separates project context from measured content. Selection observes directories as well as file names, so an empty selected folder can be distinguished from one pruned by policy. Module discovery retains the ordinary selected project names, including ancestor descriptors and Python package markers; counting/decoding then visits only selected files inside the subfolder. Context traversal errors anywhere still abort, while unrelated source read/parse failures are not measured and do not make the subtree partial. Traversal cost can remain project-wide; no proportional speedup is guaranteed.

With the same filesystem and policy, subtree records equal the corresponding whole-project file subset. Summing whole-project breakdown rows whose folder equals the subfolder or starts with it plus `/` gives an independent totals oracle. Coverage and unused-rule/exclusion findings apply to the restricted measurement; they do not justify deleting policy for other folders. Module metadata is context, not an additional source of counted lines.

## Counting

- Content kind comes from the Tokei language through reviewed data and documentation lists, recorded in full JSON as `metadata.kinds`; every other recognized language is source. A code snippet in Markdown remains documentation: its lines stay in the file's per-language `languages` counts and in `all_counted`, never in source totals, and the verbose `Not source code:` note reports their code lines. Language names unknown to the embedded Tokei get the kind `unknown`; unlike unrecognized files, they are counted.
- Docstrings count as code, as in Tokei's default: locmetry does not set Tokei's `treat_doc_strings_as_comments`, so every line inside a Python docstring, blank ones included, is a code line. This affects the languages with doc strings in Tokei 15.0.0: Python, Cython, Mojo, Raku, Bazel, Snakemake, Pony, and Roc. Doc comments such as Rust `///`, Javadoc, or TSDoc are comments as usual. Counting docstrings as comments would change totals and therefore requires a new configuration `version`.
- Other languages are counted by Locmetry's [Tokei fork](tokei-integration.md#counting-boundary), which lexes literals that Tokei 15.0.0 misreads. Character literals, such as `'"'`, protect quotes and comment markers in C, C++, C#, Go, Java, Kotlin, Rust, Scala, OCaml, F#, Haskell, Elm, PureScript and Agda, and `#\` literals in Racket, Scheme and Lisp; a Rust lifetime or a Haskell prime is not a literal. Strings are lexed in the Haskell family and the Lisp family, Go backtick strings and Java text blocks are literals, and `""` inside C# and F# `@"…"` strings is an escaped quote. Raw strings close only at a delimiter that repeats the opener's count or label: Rust `r#"…"#`, Swift `#"…"#` and `#"""…"""#`, C# `"""…"""`, C++ `R"x(…)x"`, Lua `[==[…]==]` and OCaml `{id|…|id}`, and Lua `--[==[…]==]` comments likewise. PHP `#[` attributes, the F# `(*)` operator and Ruby's `$'`, `$"` and `` $` `` globals are code. Interpolation holes are code that can hold their own strings, comments and holes: JavaScript and TypeScript `` `${…}` ``, Kotlin, Scala and Dart `${…}`, Swift `\(…)`, C# `{…}` in interpolated strings, Ruby `#{…}` and shell `$(…)` in double-quoted strings; a blank line inside a hole is blank. JavaScript, TypeScript and Ruby regular expression literals are recognized by the token before the `/`, looking past whitespace, block comments and whole-line comments; a `/` after a value, a closing bracket or an identifier other than a keyword is division. Shell `'…'` strings have no escapes, `$'…'` strings do, and `#` starts a comment only where a word can start. Shell, Ruby, PHP and Perl heredocs are literals from the line after the opener to the closing line, whose word, indentation and quoting follow each language's rules; an opener without a closing line later in the file, such as the shift in `1 << x`, is code. A Ruby regular expression may also start a line. A line that starts inside a literal is code even when its text begins with a comment marker. [Tokei counting defects](tokei-defects.md) lists the literal forms still misread, such as apostrophes in markup text and Perl's quote-like operators.
- Handlebars uses a local lexical counter because Tokei 15.0.0 treats quotes in template text as string delimiters. Apostrophes in prose must not turn later blank or comment lines into code. The counter distinguishes template text, expressions and their strings, bracketed paths, HTML attributes, comments, and raw blocks; it applies to recognized files and language mappings alike. Blank lines inside actual quoted strings count as code, and lines inside comments count as comments. Mixed code/comment lines count as code. This corrects parsing without changing the file's language, kind, or purpose. UTF-8 and BOM-directed decoding match the notebook boundary. A file-access failure is `unread`; readable bytes that cannot be decoded produce an `invalid_encoding` parse failure, no counted file record, and backend inaccuracy. This applies equally to detected and mapped templates. See the [backend correction](../src/backend/handlebars.rs) and [Handlebars expression rules](https://handlebarsjs.com/guide/expressions.html).
- Lean uses a local lexical counter because Tokei 15.0.0 declares no Lean string delimiters, so a `/-` inside a literal such as `"packet/-receipt.json"` opened a block comment that turned the rest of the file into comment lines. The counter follows Lean's lexer for strings, character literals, raw strings, `«…»` identifiers and nested block comments, and reads the `{…}` terms of `s!`, `m!` and `f!` strings as code. Other syntax that interpolates strings, such as `throwError`, is read as plain strings, which misreads only comment markers in strings nested inside its terms. Lines are classified by Tokei's rules for other languages: lines inside literals, blank ones included, count as code, a line that starts inside a comment counts as a comment even with code after the comment ends, and otherwise a line counts as a comment only when it starts and ends in a comment. Decoding, failures and mapped files behave as for Handlebars. See the [backend correction](../src/backend/lean.rs) and [Lean's lexer](https://github.com/leanprover/lean4/blob/v4.35.0/src/Lean/Parser/Basic.lean). [Tokei counting defects](tokei-defects.md) lists the defects corrected so far and those found in other languages.
- Counters are reconstructed once from original reports and nested blobs; aggregate `Total` or `children` views are not added again. A reported path counts once, even when it contributes multiple languages.
- Jupyter notebooks use a local container decoder and Tokei cell counters; the decoder supplies disjoint contributions because Tokei 15's private notebook parser overlaps parent/blob statistics and silently replaces parse failures with zeros. See [notebook semantics](#notebooks).
- `breakdown` rows in full JSON are additive. So are the top-level folders of `summary.top_folders` and the default terminal table: each covers its whole subtree, and together with the root files they cover every file once. In [subfolder mode](PRODUCT.md#subfolder-measurement), terminal rows instead show the selected folder’s immediate children and direct files, covering the measured files once. The opt-in [adaptive folder detail](PRODUCT.md#adaptive-folder-detail) replaces rows in the existing Folder table and also partitions measured source once, using existing direct/recursive aggregates without rescanning; it changes neither saved identities nor the unclaimed-folder partition. The Markdown folder table lists nested levels, where a parent includes its subfolders, so its rows cannot all be summed together.

## Limits

- Ambient Tokei configuration is not loaded. Git is not invoked, so reports do not claim a commit revision or unchanged working tree.
- Selected files that neither the backend nor a language mapping recognizes are listed in `metadata.coverage`, not proven zero LOC.
- Classification is per file, so mixed production/test files are not split, and Locmetry does not establish whether a source file is handwritten. Rust unit tests in an inline `#[cfg(test)] mod tests { … }` count with their file; moved to a `tests.rs` module file, they are tests through the `rust-test-module` convention. Reports name the lines of inline items as `inline_tests` without changing purposes: an item counts from its outer `#[cfg(test)]` attribute through its closing brace, nested items once, and Tokei counts the extracted lines, so code, comment and blank figures match the file's own. Bodiless items such as `mod tests;` count zero, as their code is counted in their own file; compound conditions such as `cfg(all(test, unix))` and inner `#![cfg(test)]` attributes are not recognized, and other languages' inline test blocks are not detected.
- Backend inaccuracy marks a measurement partial, even when the backend cannot identify affected paths. Known read and Handlebars/notebook decode/counting failures are listed separately. Failed files have no file record or measured counts; other files still contribute. [Command outcomes](PRODUCT.md#command-outcomes) owns exit-status semantics.

## Notebooks

The decoder supports notebook versions 4.0 through 4.5, with string or string-array cell sources; array fragments concatenate without inserted characters. Each cell is counted separately. Counts describe extracted source text, excluding JSON serialization, cell outputs and attachments. The decoder checks the structure needed for counting, not every metadata/output constraint of the [pinned nbformat v4.5 schema](https://github.com/jupyter/nbformat/blob/v5.10.4/nbformat/v4/nbformat.v4.5.schema.json).

Nonblank Markdown and raw-cell lines are host comments, including fenced examples; blank lines remain blanks. Code-cell text uses `language_info.name`, then `kernelspec.language`, then `language_info.file_extension` (a leading dot is accepted). Names use Tokei's case-insensitive language names. Python is the fallback only when no language declaration exists, retaining Tokei's default. An explicit unsupported declaration is not silently replaced by another language. Empty code cells and notebooks need no language inference. The `Jupyter Notebooks` host retains one language-participation file even with zero host code; embedded-language breakdown rows still have zero files.

`metadata.coverage.parse_failures` records readable files whose counts are unavailable, with root-relative `path`, stable `reason`, and explanatory `message`. Notebook reasons are `invalid_notebook` (invalid encoding, JSON or counting structure, including zero-byte input), `unsupported_notebook_version`, `unsupported_notebook_language`, and `unsupported_notebook_cell`. Unsupported content is not necessarily invalid nbformat. Any cell failure leaves the entire file uncounted, sets `backend_inaccurate = true`, and follows the [partial-measurement outcome](PRODUCT.md#command-outcomes). These paths are separate from `unread` and `unrecognized`; all three groups and counted files partition selected files. A valid empty notebook is a successfully counted zero.

New full reports and headlines always emit `parse_failures`, even when empty. Workspace paths are member-prefixed and each member emits `parse_failed_files`, including zero. The version-1 schema permits historical absence of these new fields: absent means not recorded, not no failures. Older strict schemas can reject the newly added fields and should be updated to the executable's current schema. Older successful notebook reports may contain doubled or missing counts; the new field cannot retrospectively repair them. Recognized and explicitly mapped notebook files share this behavior and BOM-aware decoding. File-access failures remain `unread`; bytes that were read but cannot be decoded are `invalid_notebook` parse failures. UTF-8 and BOM-directed decoding retain the existing supported boundary.

## Git Submodule Hints

Submodule hints read only the scan root's `.gitmodules`, without invoking Git or changing selection/classification. The reader recognizes `path` keys within named submodule sections, including the legacy dotted section form; section and key names are case-insensitive. Quoted values, escaped quotes/backslashes, `\n`, `\t`, `\b`, inline `#`/`;` comments and backslash line continuations follow [Git configuration syntax](https://git-scm.com/docs/git-config#_syntax). Quoted whitespace and comment characters remain part of the path. Includes and paths in unrelated sections are not followed or reported.

This is a best-effort scope-hint reader, not a Git configuration validator: missing/unreadable files and malformed entries supply no hints; malformed entries do not invalidate otherwise readable entries or fail measurement. It does not verify Git repository state, URLs or checkout identity. The verbose table, Markdown and JSON list only declared paths containing measured source; excluding that source removes its hint. Default tables omit these routine hints; [report content](PRODUCT.md#report-content) owns the visibility rules.

## Saved Reports

[Report compatibility](report-compatibility.md) records historical field availability and validation limits. The typed contract preserves current measurement shapes and missing failure evidence; semantic validation is used by `compare` when it reads saved reports. It cannot prove historical counting correctness.

## Private Regression

Keep real-project configurations and reports exclusively in Git-ignored `docs/research/local/`, as [CLAUDE.md](../CLAUDE.md#sensitive-analysis) requires, and verify destinations with `git check-ignore` before running. The CLI requires output files outside the scan root but does not enforce this repository-specific directory. [Output Routing](PRODUCT.md#output-routing) defines format selection and silent file exports:

```sh
cargo build --release --locked
./target/release/locmetry --root /path/to/project --config docs/research/local/project.locmetryrc --output docs/research/local/measurement.json
```

The optional guard replays saved raw backend statistics through each reviewed TOML configuration, requires the saved file records and totals, and checks reviewed example paths. It is skipped by ordinary `cargo test` runs:

```sh
LOCMETRY_PRIVATE_FIXTURES=docs/research/local/poc cargo test --locked --test integration private_regression:: -- --ignored
```

For each `<name>.locmetry.toml`, the directory must contain `<name>-measurement.json`, `<name>-measurement.tokei.json`, and `<name>.examples.json` with the checkout `root` and reviewed `examples`. The fixtures are frozen: Locmetry no longer writes raw backend statistics, so they cannot be regenerated, and the guard normalizes their older serialization instead. They predate language mappings, so files they never counted are absent from both sides. Fresh scans can differ when a working copy changes; compare equivalent snapshots before attributing differences to the counter.
