# Make Measurement Contracts Discoverable and Consistent

Research date: 2026-10-15; versions and evidence limits are defined in the [capability comparison](tool-capability-comparison.md#pin-versions-before-comparing-feature-families). **Configuration support is not a yes/no feature: discovery roots, list ordering, matching syntax, failure behavior and execution mode determine the measurement.** scc's configuration guard tests, cloc's filter diagnostics and pygount's field-level documentation offer useful lessons. Every reviewed tool also has documentation or interface gaps. Locmetry already exposes unusually detailed configuration semantics through its schemas, but its handwritten report schema and several README claims lag the actual implementation. This research records those gaps; it does not change the public contract or authorize new interfaces.

For example, invoking `scc ./project` from `/work` loads `/work/.sccconfig`, not `/work/project/.sccconfig`. `scc --config team.sccconfig` still applies the project file; adding `--no-config` isolates the explicit source. Locmetry's explicit config replaces project discovery, while `--no-user-config` separately removes personal defaults. These are source-derived examples, not executed cross-tool probes. A reproducibility recipe must state both policy sources and discovery anchors. ([scc composition tests](https://github.com/boyter/scc/blob/v4.1.0/config_test.go), [Locmetry project configuration](../PRODUCT.md#project-configuration))

**“CLI wins” is insufficient for ordered lists.** scc appends global, project and CLI category rules, then uses first-match selection. A broad earlier global rule can therefore preempt a more specific CLI rule; that consequence is a static inference, not a reproduced case. Locmetry explicitly separates first-match lists from exclusion union and precedence stages. Its personal settings cannot classify, although personal mappings can still affect which files become countable. ([scc parsing and rule construction](https://github.com/boyter/scc/blob/v4.1.0/processor/processor.go), [scc argument layering](https://github.com/boyter/scc/blob/v4.1.0/main.go), [Locmetry precedence](../PRODUCT.md#matching-and-precedence))

Pattern names also conceal differences. scc category glob `*` becomes `.*`, crossing separators; `re:` selects unanchored RE2 matching. Its `--exclude-file` is a basename substring test. Locmetry's `*` stays inside a segment, `**` spans directories, and classes/alternatives have documented semantics. cloc offers both regex and exact-list selectors with flag-specific path treatment. A copied example is useful only when its matching base and syntax travel with it. ([scc patterns](https://github.com/boyter/scc/blob/v4.1.0/processor/processor.go), [scc filename filter](https://github.com/boyter/scc/blob/v4.1.0/processor/file.go), [cloc filters](https://github.com/AlDanial/cloc/blob/v2.10/cloc#L2235), [Locmetry patterns](../PRODUCT.md#matching-and-precedence))

## Machine interfaces must preserve policy and uncertainty

scc makes a valuable authority boundary explicit: config files cannot request output writes through `--output`, `--report` or `--format-multi`, and nested config-control flags cannot load additional files. Inspected test sources cover these restrictions; those tests were not run here. However, MCP starts before CLI configuration discovery, and the inspected handlers do not reload `.sccconfig`; they use their own parameters/defaults and result structures. History has another policy path, reading ignore files from HEAD and ignoring certain working-tree flags. These modes should not be assumed equivalent. ([scc config tests](https://github.com/boyter/scc/blob/v4.1.0/config_test.go), [MCP entry](https://github.com/boyter/scc/blob/v4.1.0/main.go), [handlers](https://github.com/boyter/scc/blob/v4.1.0/mcp.go), [history policy](https://github.com/boyter/scc/blob/v4.1.0/processor/history_validation.go))

| Contract concern | Evidence and lesson |
| --- | --- |
| Missing measurement versus zero | pygount exposes `analyzed`, `binary`, `duplicate`, `empty`, `error`, `generated` and `unknown`, plus `isCountable`/`stateInfo`; clients must inspect state because uncounted records still contain zero fields. Locmetry has selected/counted/unrecognized/unread coverage, but malformed notebooks currently evade it. Reported state must describe measurement availability, not merely successful file opening. [pygount state model](https://github.com/roskakori/pygount/blob/v3.2.0/pygount/analysis.py#L74), [notebook findings](tool-lessons-and-gaps.md#notebooks-break-two-existing-measurement-guarantees) |
| Diagnostics and exit status | scc read warnings require verbose mode and write to stdout; machine output can therefore encounter diagnostics. cloc errors are outside report serialization and quiet can suppress them. Tokei machine output returns success even when inaccurate; gocloc source has unchecked scanner errors; pygount records file errors without necessarily failing the overall command. These are source findings, not runtime-tested peer failures. Locmetry's separate stderr and I/O-partial exit 2 are useful, but do not detect every parsing failure. [scc logging](https://github.com/boyter/scc/blob/v4.1.0/processor/trace.go), [cloc report tail](https://github.com/AlDanial/cloc/blob/v2.10/cloc#L1750), [Tokei main](https://github.com/XAMPPRocky/tokei/blob/v15.0.0/src/main.rs), [gocloc parser](https://github.com/hhatto/gocloc/blob/v0.7.0/file.go), [pygount command](https://github.com/roskakori/pygount/blob/v3.2.0/pygount/command.py#L495), [Locmetry exits](../../src/main.rs) |
| Version and schema | pygount has an independent `formatVersion` and a field-level JSON reference. scc `json2` is a different shape, not an in-document schema version. No peer equivalent of Locmetry's `--schema config/user-config/workspace/report` was found in the inspected surfaces; API types and MCP input descriptions provide narrower discovery. [pygount JSON](https://github.com/roskakori/pygount/blob/v3.2.0/docs/json.md), [scc JSON](https://github.com/boyter/scc/blob/v4.1.0/processor/formatters_json.go), [Locmetry schemas](../../src/config/schema.rs) |
| Provenance | Locmetry records effective configuration, backend settings, modules and per-file classification/mapping IDs. These do not fingerprint source, ignore-file contents or executable build, and reports do not claim a Git revision. A matching policy receipt is useful evidence, not proof that only source edits caused a later difference. [Report contract](../PRODUCT.md#reporting-and-coverage), [measurement limits](../measurement.md#limits), [net-change semantics](../proposals/net-change.md) |
| Disabled versus measured zero | scc ordinary JSON omits disabled cognitive complexity but retains a measured zero; MCP's separate response type leaves disabled cognitive values at zero. Locmetry's omitted summary zeros, optional file detail and unavailable measurements likewise require explicit distinct semantics in every interface. [scc types](https://github.com/boyter/scc/blob/v4.1.0/processor/structs.go), [MCP results](https://github.com/boyter/scc/blob/v4.1.0/mcp.go), [Locmetry reporting](../PRODUCT.md#reporting-and-coverage) |

Locmetry config schemas are generated from parser types and enriched from shared constants; the report schema is assembled manually beside separately assembled JSON. Its count integers lack a nonnegative minimum, effective-policy objects are broadly unconstrained, and dynamic maps do not uniformly reject unknown structure. Structural acceptance tests do not establish rejection of invalid inputs or arithmetic correctness. The [existing proposal](../proposals/net-change.md) already calls for shared typed contract ownership; the audit supports that direction without adding a third independent schema mechanism. Schema descriptions must also explain overlapping source-language file counts versus additive breakdown rows with embedded `files = 0`. ([Config schema implementation](../../src/config/schema.rs), [report schema implementation](../../src/report_schema.rs), [schema tests](../../tests/schema.rs), [aggregation](../../src/report.rs))

The recommendation is to treat documentation as a consumer of the same contract as the CLI and schemas. Test examples where defaults, missing values and failures matter; explain scope before metric interpretation; make versioned executable help authoritative. A dedicated MCP server is not required to achieve this. If a second interface is later needed, it should reuse policy and result semantics rather than introduce another measurement dialect.
