## Test to Production Ratio Presentation — Awaiting Further Direction

**Status, 2026-10-16:** external review incorporated; plan update only. The selected design extends neutral ratio columns and uses no value-dependent color bands or highlighting. Implementation remains on hold under the owner’s earlier instruction. PRODUCT, README, executable schemas and current behavior are unchanged.

**Research conclusion.** Published ranges exist but are descriptive: Khorikov reports `1–3` for a heavily tested subset of enterprise projects; measured industrial TDD teams reported `0.39–0.89`. Practitioner recommendations conflict, from approximately `1` in Martin and the XP ideal reported by van Deursen to Hansson’s warnings at code:test `1:2` and `1:3`, whose notation Martin disputed. Several practitioners reject the ratio as a quality metric; none of the reviewed evidence validates a cutoff against defects or maintenance cost. Khorikov’s much higher example and Beck’s coupled compiler illustrate context dependence, not a general rule that every value above `3` is exceptional. The reviewed ratio passages do not establish a common LOC counting definition comparable to Locmetry’s code-only lines, so numerical comparisons are approximate. The owner’s `2.0` and `1.5` examples were prompts for research, not selected thresholds.

**Selected scope after review.** Retain the existing folder, subfolder and workspace-repository `Test/prod` columns; add the ratio to language rows and their total row in terminal tables and Markdown. Skip purpose/category rows already split by purpose, non-source data/documentation rows, and ratios of signed comparison deltas. The metric describes where classified tests and production code reside; it does not establish which code those tests exercise. The language-table legend must explicitly note that tests written in another language than the code they test can distort per-language ratios, such as Kotlin tests for Java production code.

**Why show it.** Ratios provide factual composition without requiring manual division, and can prompt investigation of classification. A zero ratio in a project known to have tests may indicate missed test rules; a surprisingly high ratio may prompt checking whether fixtures or generated code were classified as test source. Neither observation diagnoses a problem by itself.

**Why no bands or highlighting.** The review reverses the earlier recommendation for a soft amber cue above `3`. Khorikov supplies descriptive context, not a boundary that makes higher values suspect; Beck, Cooper and Fowler caution against treating the ratio as a quality signal. A cue would offer little benefit in ordinary single-root output while requiring rules for unclassified code, rounding, subfolder scope, styling and explanation. Keep all positive ratios neutral regardless of magnitude, including values around `1`, `1.5`, `2` and `3`. There is no reference-band styling, warning threshold or automatic red. Existing gray `-` and `0.00` remain factual undefined/zero treatment, not judgments; normal table hierarchy may still emphasize total rows.

**Arithmetic and presentation.** Use classified source `Test / Production`, excluding unclassified code. Calculate totals from summed test and production counts, never an average of row ratios. Show `-` when production is zero, including test-only rows; show `0.00` when production is positive and test code is zero, retaining existing two-decimal formatting. Keep Markdown portable without HTML color markup and leave JSON evidence unchanged. Reuse the existing ratio routine and presentation roles; no new role, custom threshold, theme setting, scope exception or CI policy is needed.

**Deferred cue rationale.** The initial alternative was a neutral descriptive `1–3` band with soft amber above `3`; the later review narrowed the cue to an underline above `3` on whole-project rows only, conditional on an unclassified-code check. Both are product heuristics rather than literature-backed limits and are retained only as rejected designs for this change. Revisit discoverability if an actual workflow comparing many repositories demonstrates that outliers are hard to spot; evaluate sorting or a separate note before adding color. No cue implementation is scheduled.
